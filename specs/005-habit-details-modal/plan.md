# Implementation Plan: Habit Details Modal

**Branch**: `feature/005-habit-details-modal` | **Date**: 2026-11-05 | **Spec**: [spec.md](spec.md)

**Input**: `specs/005-habit-details-modal/spec.md`

**Baseline**: The branch is based on `main` commit `672c98a`, which includes habit deletion from
PR #1 and version 0.3.0. Versioning and publication follow [the release guide](../../docs/releasing.md)
after implementation and validation.

## Summary

Open one habit's history and editor in a native Obsidian modal from its name. Replace the inline
history and management sections with this surface and a compact archived-habit list. Reuse existing
history calculations, current-state summaries, mutations, and deletion safeguards. The change adds
view-local presentation state and scoped styles; existing habit notes remain compatible.

## Technical Context

**Language/Version**: TypeScript 5.9.3, strict mode; ES2020 build target; Node.js 24.21.0 tooling.

**Primary Dependencies**: Obsidian API 1.14.4, existing native DOM/CSS rendering, esbuild 0.28.2.
No additional runtime or development dependency is required.

**Storage**: Existing version-1 Markdown notes and settings. Session drafts live only in each
`HabitDashboardView`; no data-format change, migration, or persisted UI preference.

**Testing**: Vitest 5.0.5, jsdom 30.1.3, existing Obsidian mocks and integration harnesses; native
Obsidian and supported mobile environments for focus, layout, and keyboard acceptance.

**Target Platform**: Obsidian desktop, iOS, and Android, retaining `minAppVersion: 1.14.4` and
`isDesktopOnly: false`.

**Project Type**: Existing single-project Obsidian plugin.

**Performance Goals**: Preserve the existing daily marking path. Project yearly history only for
an open habit; do not add presentation-time vault reads or remount active form fields on refresh.
Meet the one/two-activation and 30-second acceptance goals in the spec.

**Constraints**: Offline; Obsidian themes and language; 320-pixel narrow layout; 44-by-44 layout-pixel
touch targets; native keyboard/dismissal; one vertical scroller; preserved guarded writes and deletion.

**Scale/Scope**: Personal habit collections, one details modal per dashboard view, one selected year
per modal. No new capacity limit, bulk workflow, external service, or general UI state framework.

## Phase 1: Design

### Ownership and projection

- Add `getHabitDetail(habitId, year)` to the controller. Return the validated current summary plus
  the existing `HabitHistory`, or null for an unavailable identity; clamp the year to creation/today.
  The projection is synchronous and performs no I/O.
- Remove shared selected-habit/year fields, `DashboardViewModel.detail`, and their obsolete
  toggle/close/year-selection handlers. The modal owns that selection, so separate dashboard leaves
  cannot open or navigate one another's dialogs.
- Forward the view's existing subscription to both dashboard and open-modal updates. Expose the
  controller's existing `settingsChanging` flag in the view model so teardown can happen on its
  synchronous notification, including while settings persistence is waiting.

### Editor and session state

- Keep dirty name/target values in a view-local map keyed by habit ID. A new modal shows its editor
  before history and restores any retained draft for that valid habit. A live preview reflects
  name/target drafts without submitting them; the header contains only the habit name.
- Keep active editor input nodes mounted on ordinary updates. Update saved labels, pristine fields,
  and lifecycle controls in place. Update the calendar in a separate subtree, retaining its scroll
  for the same year and the modal's vertical scroll.
- Compare against the previous saved baseline before applying an incoming projection. Await field
  submissions, clear only the successfully submitted matching draft, and preserve other or newer
  input. Preserve concrete `WriteResult | null` return types for rename/target in the extracted
  editor's handler contract. Stable field keys support focus across rename/localization changes.
- Cancel owned unconfirmed deletion on teardown, clear the active modal reference before callbacks
  that emit, and clear cached drafts on view close or folder/controller replacement.

### Deletion, feedback, and invalidation

- Present the prepared request's existing short question in the same dialog. Use the controller's
  existing prepare/cancel/confirm methods and per-habit protection; the modal adds no deletion engine.
- Guard asynchronous preparation against a closed or replaced modal/controller. Teardown cancels
  its own preparation/request once; a late continuation does not reopen or cancel a newer session.
- Track UI submission lifetime separately from `isDeletionPending`, which is false during commit.
  Do not misreport expected disappearance during the modal's own deletion. Close on successful
  removal; preserve failure/uncertainty on the visible surface and through existing settings rebind.
- Route the existing controller message into the open modal and suppress background error focus.
  On dismissal, show it normally on the dashboard. A failed discovery retains the last successful
  snapshot; do not turn loading or a load error into a false missing-habit result.

### Archived access and responsive presentation

- Derive the archive disclosure/count from current-state summaries, not the viewed week's rows.
  Reuse their existing sort order, and omit the disclosure when no valid archived habits exist.
- Count duplicate names across all summaries; use note paths in affected grid/list/modal labels.
  Keep existing historical row inclusion and eligibility rules.
- Put the always-visible editor fields before the history body. Use a labeled native dialog,
  title initial focus, Cancel initial focus for confirmation, and deterministic return focus.
- Add a dedicated modal surface/container and share only required theme tokens and selectors.
  Extend icon/editor/touch styling into that scope. Retain calendar-only horizontal scrolling.
  Use native sizing first; add a local viewport correction only for a demonstrated device defect.

## Accepted implementation additions — 2026-11-06

Creation and rename now check comparison names against freshly discovered valid active/archived
habits. The comparison key trims, normalizes Unicode NFC and lowercases without changing stored
names. A small queue per requested name serializes collisions while keeping unrelated names and
habits usable. Existing duplicate notes remain valid and are never cleaned up automatically; the
same comparison key also controls path disambiguation in entry points and details.

Native QA demonstrated that the host allowed Tab to escape, exposed its close affordance through
a newer CSS class, and clipped long mobile titles. Scoped handling cycles visible enabled controls,
restores background inert state with ownership across views, labels/enables the host close control,
and focuses the title after native opening. No general host simulator was added.

The chooser floats beside its trigger without reflowing the form, using the public browser popover
API with a positioned fallback. It keeps the existing local search and 30-result pagination, closes
on selection, and dismisses before details on Escape. Outside click/close dismiss without saving.
Viewport resize/scroll repositions the panel; disposal releases its temporary listeners. No note schema, dependency, migration, automatic cleanup, or global state
framework is introduced. Real-device software keyboards remain a separate acceptance check.
